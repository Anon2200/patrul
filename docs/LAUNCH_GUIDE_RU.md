# Подготовка к запуску «Патруля»

Инструкция относится к актуальной кодовой базе ветки `main`. Изменение кода в GitHub само по себе не подтверждает, что Production на ONREZA обновлён. Публикация на ONREZA выполняется только по отдельной команде владельца проекта.

## 1. Обязательная подготовка базы

Перед обновлением рабочей версии:

1. Сделать резервную копию Production PostgreSQL.
2. Проверить восстановление этой копии на отдельной тестовой базе.
3. Проверить наличие и доступность действующего `PATRUL_DATA_ENCRYPTION_KEY`.
4. Убедиться, что `DATABASE_URL` указывает на нужную Production-базу.
5. Прочитать описание миграции 010 в `docs/DATABASE_SETUP.md`: при первом запуске новой схемы старые ежедневные наряды из прежнего поля не переносятся. Переносятся только назначения и подмены графика.

Не меняйте ключ шифрования при обычном обновлении приложения. Не проводите экспериментальные миграции на рабочей базе.

## 2. Переменные окружения ONREZA

Для приложения в окружении Production должны быть настроены:

| Переменная | Требование |
|---|---|
| `DATABASE_URL` | Действующая строка PostgreSQL |
| `PATRUL_PUBLIC_ORIGIN` | Точно `https://patrul-ippolitovartem63-ms5l.onreza.app`, без завершающего слеша |
| `PATRUL_DATA_ENCRYPTION_KEY` | 32 случайных байта в base64url или 64 hex-символа |
| `PATRUL_BOOTSTRAP_SECRET` | Временный случайный секрет минимум 32 байта; нужен только для первичного создания администратора |
| `PATRUL_TIME_ZONE` | Необязательно; по умолчанию `Europe/Moscow` |
| `PATRUL_TRUST_PROXY` | Необязательно; по умолчанию учитывается адрес из `X-Forwarded-For` (нужен за прокси ONREZA, чтобы лимит неудачных входов считался по каждому пользователю). `0` отключает |

Сгенерировать каждый случайный секрет отдельно в локальном терминале:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

Значения не отправлять в чат и не сохранять в репозитории. Ключ шифрования хранить отдельно от БД и резервных копий. Потеря ключа означает невозможность расшифровать рабочие данные. Не заменять ключ без процедуры ротации.

Не включать `PATRUL_LEGACY_ROLE_TOKENS_ENABLED=true`: рабочая авторизация использует персональные сессии. После создания первой учётной записи удалить `PATRUL_BOOTSTRAP_SECRET` и перезапустить сервис.

## 3. Первичная настройка и роли

Первичная учётная запись — Старший мастер (`uchet`) с признаком системного администратора. После создания учётной записи Старшего мастера:

1. Войти под ней и открыть управление сотрудниками.
2. Создать учётные записи Начальника (`nachalnik`), Заместителя (`zam`) и Документоведа (`dokumentoved`).
3. Передать временные пароли сотрудникам лично. При первом входе они должны установить собственный пароль.
4. Для каждого Старшего патруля выдать одноразовый код активации в рабочем центре. Код действует ограниченное время и используется один раз.
5. Старший патруля при первом входе подтверждает фамилию, вводит код и самостоятельно задаёт PIN из шести цифр. Последующие входы выполняются по фамилии и PIN.

Отдельная пользовательская роль обычного патрульного не предусмотрена.

## 4. Приёмочная проверка после согласованного обновления

Проверять в браузере на реальном адресе Production только после того, как владелец отдельно разрешит публикацию и площадка покажет успешный статус запуска.

- Проверить вход и доступность назначенного кабинета для каждой из пяти ролей.
- Проверить, что сотрудник не может открыть кабинет другой роли напрямую.
- Добавить тестовую запись в каждом основном разделе, дождаться подтверждения сохранения, обновить страницу и проверить запись.
- В разделе «Личный состав» добавить тестового сотрудника, проверить отсутствие дублей и одинаковое отображение актуального списка в кабинетах, затем удалить тестовую запись.
- Проверить назначения отделений на разные посты в разные даты и чтение общего календаря.
- Проверить дневной наряд: добавление/перенос отделения, пересборку выбранной даты и всех дат, сохранение времён и отметок.
- Проверить, что Старший патруля видит только назначенное ему отделение и не может открыть полный дневной наряд.
- Проверить выдачу оборудования только Старшему патруля, подписи и печатный бланк.
- Проверить общие поручения, уведомления, электронную почту и обмен зашифрованными пакетами.
- Проверить контрольный просмотр кабинетов Старшим мастером: просмотр доступен только для чтения и регистрируется в аудите.
- Проверить работу с двух устройств и конфликт одновременного изменения.
- Проверить резервное копирование и восстановление PostgreSQL на отдельной базе.

Тестовые записи удалять только после подтверждения их синхронизации и сохранения нужных рабочих данных.

## 5. Синхронизация и ограничения

- Синхронизация основных кабинетов требует интернета; перед закрытием страницы дождитесь статуса сохранения.
- Старший патруля может продолжить журнал смены офлайн в той же ранее авторизованной вкладке в пределах восьми часов. Офлайн-очередь шифруется и отправляется после повторной проверки сессии.
- Первый вход, новое устройство, изменение PIN, почта и серверные поручения не следует считать доступными офлайн.
- JSON-резервные копии и CSV-экспорты содержат открытые данные; храните их в защищённом месте.
- Ограничитель попыток входа хранит счётчики в памяти одного процесса. Несколько реплик и reverse proxy требуют отдельной эксплуатационной проверки.
