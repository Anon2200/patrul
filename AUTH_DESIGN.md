# Индивидуальная авторизация «Патруля»

Статус: основная реализация находится в ветке `launch-hardening` и включена в PR #5. Production пока не обновлён.

## Модель доступа

- Четыре рабочие роли: `nachalnik`, `zam`, `uchet`, `dokumentoved`.
- Публичной регистрации нет.
- Первая учётная запись создаётся через `PATRUL_BOOTSTRAP_SECRET`; это Старший мастер (`uchet`) с отдельным признаком системного администратора.
- Старший мастер создаёт учётные записи сотрудников, назначает им рабочую роль, блокирует/разблокирует, сбрасывает пароль и просматривает аудит.
- Системный администратор не получает доступ к данным других рабочих ролей только из-за административного статуса: рабочие данные доступны по назначенной роли.
- Начальник и другие сотрудники не могут самостоятельно назначать роли или административные права.

## Реализованная защита

- Пароли хэшируются через Node.js scrypt с фиксированными параметрами и индивидуальной солью.
- Сессионный токен генерируется случайно; в браузере хранится в Secure, HttpOnly, SameSite=Lax cookie, в PostgreSQL — только хэш токена.
- Сессия ограничена по сроку; выход, блокировка и сброс пароля отзывают сессии.
- Для изменяющих запросов обязательны CSRF-токен и точное совпадение Origin с `PATRUL_PUBLIC_ORIGIN`.
- Вход ограничен по IP и логину; ошибки входа не раскрывают существование пользователя.
- Сотрудник обязан сменить временный пароль при первом входе.
- Создание/изменение/блокировка сотрудников, сброс пароля, вход и выход записываются в журнал аудита.
- Старый Bearer API выключен по умолчанию; новая клиентская версия использует персональные сессии.

## Проверки

GitHub Actions проверяет bootstrap, персональный вход, CSRF/Origin, ролевой доступ, обязательную смену временного пароля, блокировку, сброс пароля, отзыв сессий, rate limit, истечение сессии и аудит. Ручная проверка интерфейса в браузере остаётся обязательной перед Production.

## Шифрование данных

Рабочие данные каждой роли шифруются AES-256-GCM в сервере до сохранения в PostgreSQL. В БД хранится зашифрованный envelope, а не исходный JSON. Ключ `PATRUL_DATA_ENCRYPTION_KEY` должен содержать ровно 32 случайных байта в формате base64url или 64 hex-символа. Потеря ключа означает потерю доступа к зашифрованным данным; ключ нужно отдельно резервировать и не менять без процедуры ротации.

При запуске сервер мигрирует старые открытые строки и проверяет уже зашифрованные строки. При неверном ключе или повреждении шифротекста сервер не должен начать обслуживать запросы.

## Оставшиеся ограничения

- Ограничитель попыток входа хранит счётчики в памяти одного процесса; reverse proxy и несколько реплик требуют отдельной проверки.
- Ручные JSON/CSV экспорты не шифруются.
- Нужны ручные браузерные испытания четырёх ролей, двух устройств, межролевого обмена и конфликта версий.
- Нужны резервное копирование и проверенное восстановление PostgreSQL.
- Автоматический CI не заменяет независимый аудит и проверку production-конфигурации.

Подробная последовательность настройки и запуска находится в `LAUNCH_GUIDE_RU.md`.
