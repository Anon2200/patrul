# Проектирование индивидуальной авторизации

Статус: частичная реализация в отдельной ветке, не готово к эксплуатации. Production не изменён. Автоматическая миграция выполняется только при запуске версии этой ветки и должна быть предварительно проверена на отдельной БД.

## Цель

Заменить общие пароли четырёх ролей персональными учётными записями. Каждое действие должно быть связано с конкретным сотрудником, а доступ должен проверяться сервером на каждом запросе.

## Предлагаемая модель

- Учётная запись: уникальный логин, отображаемое имя, роль, хэш пароля, состояние (активна/заблокирована), даты создания и изменения.
- Роли приложения остаются: `nachalnik`, `zam`, `uchet`, `dokumentoved`. Роль хранится на сервере; клиент не может назначить себе другую роль.
- Самостоятельная публичная регистрация запрещена.
- Пароли хранятся только как стойкие хэши с индивидуальной солью (предпочтительно Argon2id; если среда не поддерживает надёжную сборку — Node.js scrypt с проверенными параметрами).
- Сервер требует точный `PATRUL_PUBLIC_ORIGIN`, не использует Host-заголовок как запасной источник доверия и отдаёт HSTS.
- Серверные сессии: случайный непрозрачный токен в cookie `Secure; HttpOnly; SameSite=Lax; Path=/`; в PostgreSQL хранится только хэш токена. Ограниченный срок жизни, ротация после входа и изменения прав, отзыв при выходе/блокировке.
- Защита от CSRF: отдельный непредсказуемый CSRF-токен для изменяющих запросов, проверка Origin/Referer и обязательный нестандартный заголовок.
- Ограничение частоты входа по IP и логину, единообразные ошибки входа, безопасное восстановление доступа.
- Журнал аудита: входы, выходы, отказы, создание/блокировка учётных записей, смена ролей и изменения рабочих данных. Не записывать пароли, токены и полные документы.
- API возвращает только данные, разрешённые текущей серверной сессии и роли. Удалить ролевые Bearer-секреты из браузерного кода после проверенной миграции.
- Управление учётными записями выполняет Старший мастер (роль приложения `uchet`) — владелец системы. Его право управления пользователями хранится как отдельный серверный признак `is_system_admin`, а не выводится из названия рабочей роли. Он может создавать сотрудников всех четырёх рабочих ролей, менять их данные и роли, блокировать/разблокировать учётные записи, выдавать временный пароль для сброса и отзывать их активные сессии. Все такие действия аудируются. Другие сотрудники не получают эти полномочия только из-за своей рабочей роли.

## План реализации и проверки

1. Утверждено: первую учётную запись системного администратора создают одноразовым секретом первичной настройки; это будет учётная запись Старшего мастера (`uchet`) с отдельным признаком `is_system_admin`.
2. Реализовано: таблицы пользователей, сессий и аудита с ограничениями и индексами; миграция выполняется при старте сервера этой ветки.
3. Реализован API первичного создания администратора через секрет окружения `PATRUL_BOOTSTRAP_SECRET` (не менее 32 байт); секрет не хранится в Git. Первичная форма доступна в клиенте, но Production-переменная ещё не настроена.
4. Частично реализовано: персональный вход/выход, непрозрачные Secure HttpOnly SameSite cookie-сессии, хэш сессии в PostgreSQL, CSRF-проверка Origin и отдельного заголовка, смена временного пароля, отзыв сессий при блокировке/сбросе пароля, ограничение попыток входа.
5. Реализован новый `/api/session-data/:role` с серверной проверкой рабочей роли и CSRF для записи. Старый Bearer API выключен по умолчанию и оставлен только для изолированных compatibility-тестов через `PATRUL_LEGACY_ROLE_TOKENS_ENABLED=true`.
6. Клиентский синхронизатор переведён на персональную сессию; добавлена панель Старшего мастера для создания сотрудников, назначения рабочих ролей, блокировки/разблокировки, сброса временного пароля и просмотра журнала действий. Требуется ручная проверка интерфейса на реальных браузерах.
7. CI успешно проверяет bootstrap, персональный вход, CSRF/Origin, разграничение ролей, обязательную смену временного пароля, блокировку и сброс пароля с отзывом сессий, rate limit, истечение сессии, AES-256-GCM хранение и миграцию старых открытых строк. Не покрыты все сценарии конкуренции, ротации сессий и восстановления.
8. Провести миграцию только в отдельной тестовой БД с тестовыми данными; подготовить резервное копирование и план отката.
9. Независимо проверить реализацию и только после этого рассматривать Production.

## Решения, требующие подтверждения владельца системы

- Утверждено владельцем: учётные записи всех сотрудников создаёт и администрирует Старший мастер; отдельная должность системного администратора не нужна.
- Начальник не управляет учётными записями и не может назначать себе или другим административные полномочия. Только системный администратор-Старший мастер может менять рабочие роли. Нельзя снять собственные административные права или заблокировать последнюю активную учётную запись системного администратора; для таких действий потребуется заранее назначенная резервная учётная запись администратора.
- Как сотрудники получают первоначальный пароль и восстанавливают доступ? Рекомендуется выдача временного одноразового пароля лично администратором с обязательной сменой при первом входе; публичное восстановление по email не включать без подтверждённой почтовой инфраструктуры.

## Важное ограничение

Наличие этого проекта решения или успешных CI-тестов не означает, что система готова для реальных служебных/персональных данных. До завершения разработки, независимой оценки безопасности, проверки резервного восстановления и юридической оценки такие данные не вводить.


## Подготовленная схема БД

Файл `migrations/001_identity_schema.sql` содержит черновую схему таблиц пользователей, серверных сессий и аудита. Она:
- хранит только хэш пароля и хэш случайного токена сессии;
- отделяет рабочую роль сотрудника от полномочия системного администратора;
- предусматривает отзыв сессий при блокировке или сбросе пароля;
- фиксирует тип события, инициатора и цель административного действия;
- не содержит реальных учётных записей, паролей или данных сотрудников.

Схема автоматически применяется сервером при запуске этой ветки; CI проверяет её на отдельной тестовой PostgreSQL. К Production миграция не применялась.


## Фактически реализовано в ветке

- `auth.js`: scrypt-хэширование паролей (фиксированные параметры N=32768, r=8, p=1), индивидуальные сессии, CSRF, API управления пользователями и журнал аудита.
- `cloud-sync.js`: персональный вход вместо общего пароля роли; серверная cookie-сессия; экран первичной настройки; панель управления сотрудниками для системного администратора.
- `server.js`: автоматическое применение схемы идентификации при старте; новый session API; старый Bearer API закрыт по умолчанию.
- Интеграционные и статические проверки CI успешно прошли на коммите `563c16b299909be8b18edafe45192cff8ba6a438`: 21/21 интеграционных тестов, синтаксис и статические проверки страниц, SQL-схема на отдельной PostgreSQL.

## Шифрование данных приложения

- Добавлен `data-crypto.js`: шифрование данных ролей на уровне приложения с AES-256-GCM; в PostgreSQL в колонке JSONB хранится только envelope с IV, тегом аутентификации и ciphertext.
- В качестве AAD используется версия формата и роль, чтобы ciphertext нельзя было незаметно перенести между ролями.
- Пароль шифрования межролевых пакетов (`sx.pw`) теперь сохраняется в составе зашифрованных данных роли, чтобы не теряться после перезагрузки; он не включается в скачиваемый локальный JSON backup.
- Передача между ролями всегда использует AES-GCM; отправка без общего пароля длиной не менее 16 символов заблокирована, а старые незашифрованные пакеты отклоняются.
- Старые незашифрованные строки шифруются при первом чтении с условием по версии, чтобы не затереть параллельную запись.
- Сервер не запускается без `PATRUL_DATA_ENCRYPTION_KEY` (32 случайных байта, base64url или 64 hex). Ключ должен храниться только в секретах окружения, отдельно от БД; резервировать его отдельно и безопасно, иначе данные невозможно расшифровать. Для генерации подходит `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`. Этот ключ нельзя менять без процедуры ротации и нельзя терять: без него зашифрованные данные не восстановить.
- Интеграционные тесты проверяют хранение ciphertext и миграцию старых строк; ручные тесты и независимая проверка реализации всё ещё обязательны.

## Обязательные задачи до допуска к эксплуатации

- CI успешно прошёл на коммите `4b6528b` (21/21 интеграционных тестов). После любых дальнейших изменений CI требуется запускать повторно.
- Проверить поведение cookie и Origin за реальным reverse proxy, а также обработку oversized/malformed запросов в production-конфигурации.
- Добавить надёжную первичную настройку и безопасный процесс хранения/ротации bootstrap-секрета.
- Перед отдельным Production-деплоем задать `PATRUL_DATA_ENCRYPTION_KEY` как секрет (32 случайных байта), `PATRUL_PUBLIC_ORIGIN` как точный HTTPS-адрес сайта и `PATRUL_BOOTSTRAP_SECRET` как одноразовый секрет минимум 32 байта; после создания первого Старшего мастера удалить bootstrap-секрет. Эти переменные ещё не настраивались в Production.
- Дополнить тесты конкурирующими bootstrap-запросами, ротацией сессий, повторной отправкой, проверкой полноты аудита и процедурой восстановления.
- Провести ручные браузерные тесты всех четырёх ролей и межролевого обмена.
- Проверить политику хранения/резервирования/шифрования, доступ к PostgreSQL и размещение данных; провести независимый аудит безопасности и юридическую оценку.
- В рабочей ветке устранена постоянная запись основного состояния приложения в `localStorage`: после подтверждённой серверной синхронизации старый кэш роли удаляется; при несохранённых изменениях браузер предупреждает о закрытии вкладки. До успешной персональной авторизации старый локальный кэш не загружается в память приложения; после входа он читается только для миграции и удаляется после успешного сохранения/загрузки с сервера. Конфликт локальной и серверной версий блокирует доступ до разрешения конфликта. При этом память вкладки содержит открытые данные во время работы, а скачиваемые вручную JSON-резервные копии и CSV-экспорты не зашифрованы и требуют защищённого хранения. Нужны ручные браузерные тесты, включая выход и общие устройства.
- Не включать legacy bearer API в Production. Не развёртывать ветку и не переносить служебные/персональные данные до выполнения release gate.
