# Проектирование индивидуальной авторизации

Статус: проект решения, не готово к эксплуатации. Этот документ не включает изменения Production и не мигрирует существующие данные.

## Цель

Заменить общие пароли четырёх ролей персональными учётными записями. Каждое действие должно быть связано с конкретным сотрудником, а доступ должен проверяться сервером на каждом запросе.

## Предлагаемая модель

- Учётная запись: уникальный логин, отображаемое имя, роль, хэш пароля, состояние (активна/заблокирована), даты создания и изменения.
- Роли приложения остаются: `nachalnik`, `zam`, `uchet`, `dokumentoved`. Роль хранится на сервере; клиент не может назначить себе другую роль.
- Самостоятельная публичная регистрация запрещена.
- Пароли хранятся только как стойкие хэши с индивидуальной солью (предпочтительно Argon2id; если среда не поддерживает надёжную сборку — Node.js scrypt с проверенными параметрами).
- Серверные сессии: случайный непрозрачный токен в cookie `Secure; HttpOnly; SameSite=Lax; Path=/`; в PostgreSQL хранится только хэш токена. Ограниченный срок жизни, ротация после входа и изменения прав, отзыв при выходе/блокировке.
- Защита от CSRF: отдельный непредсказуемый CSRF-токен для изменяющих запросов, проверка Origin/Referer и обязательный нестандартный заголовок.
- Ограничение частоты входа по IP и логину, единообразные ошибки входа, безопасное восстановление доступа.
- Журнал аудита: входы, выходы, отказы, создание/блокировка учётных записей, смена ролей и изменения рабочих данных. Не записывать пароли, токены и полные документы.
- API возвращает только данные, разрешённые текущей серверной сессии и роли. Удалить ролевые Bearer-секреты из браузерного кода после проверенной миграции.
- Управление учётными записями выполняет Старший мастер (роль приложения `uchet`) — владелец системы. Его право управления пользователями хранится как отдельный серверный признак `is_system_admin`, а не выводится из названия рабочей роли. Он может создавать сотрудников всех четырёх рабочих ролей, менять их данные и роли, блокировать/разблокировать учётные записи, выдавать временный пароль для сброса и отзывать их активные сессии. Все такие действия аудируются. Другие сотрудники не получают эти полномочия только из-за своей рабочей роли.

## План реализации и проверки

1. Утверждено: первую учётную запись системного администратора создают одноразовым секретом первичной настройки; это будет учётная запись Старшего мастера (`uchet`) с отдельным признаком `is_system_admin`.
2. Добавить таблицы пользователей, сессий и аудита с ограничениями и индексами.
3. Добавить безопасное первичное создание администратора через одноразовый секрет окружения; секрет не хранить в Git и не показывать в браузере.
4. Реализовать вход, выход, проверку сессии, CSRF, отзыв сессий и административные операции.
5. Перевести API данных на сессию и серверную проверку роли; добавить тесты всех разрешённых и запрещённых комбинаций.
6. Обновить клиентский интерфейс четырёх ролей и сценарии обмена документами.
7. Проверить конкурентные сессии, блокировку пользователя, отзыв активных сессий, истечение срока, CSRF, перебор паролей, аудит и восстановление.
8. Провести миграцию только в отдельной тестовой БД с тестовыми данными; подготовить резервное копирование и план отката.
9. Независимо проверить реализацию и только после этого рассматривать Production.

## Решения, требующие подтверждения владельца системы

- Утверждено владельцем: учётные записи всех сотрудников создаёт и администрирует Старший мастер; отдельная должность системного администратора не нужна.
- Начальник не управляет учётными записями и не может назначать себе или другим административные полномочия. Только системный администратор-Старший мастер может менять рабочие роли. Нельзя снять собственные административные права или заблокировать последнюю активную учётную запись системного администратора; для таких действий потребуется заранее назначенная резервная учётная запись администратора.
- Как сотрудники получают первоначальный пароль и восстанавливают доступ? Рекомендуется выдача временного одноразового пароля лично администратором с обязательной сменой при первом входе; публичное восстановление по email не включать без подтверждённой почтовой инфраструктуры.

## Важное ограничение

Наличие этого проекта решения или успешных CI-тестов не означает, что система готова для реальных служебных/персональных данных. До завершения разработки, независимой оценки безопасности, проверки резервного восстановления и юридической оценки такие данные не вводить.


## Подготовленная схема БД

Файл `migrations/001_identity_schema.sql` содержит черновую схему таблиц пользователей, серверных сессий и аудита. Она:
- хранит только хэш пароля и хэш случайного токена сессии;
- отделяет рабочую роль сотрудника от полномочия системного администратора;
- предусматривает отзыв сессий при блокировке или сбросе пароля;
- фиксирует тип события, инициатора и цель административного действия;
- не содержит реальных учётных записей, паролей или данных сотрудников.

Миграция пока не запускается сервером и не применялась к Production или существующей базе. Перед использованием её нужно проверить на отдельной тестовой PostgreSQL и добавить тесты ограничений и административных сценариев.
